폰·좌석 태블릿·딜러 화면·전광판 네 단말이 한 상태를 공유하는 오프라인 홀덤 토너먼트
운영 서버입니다. 카드는 사람 딜러가 실물로 돌리고, 칩과 팟, 좌석, 상금은 서버가 관리합니다.

V1 MVP는 "돌아가긴 한다"에서 멈춰 있었습니다. V2는 그 코드를 가져와 "정확하게 돌아간다"로
옮기는 작업입니다. 구현은 에이전트 코딩으로 진행했고, 무엇을 검증할지와 무엇을 하지
않을지는 직접 정했습니다.

## 에이전트 작업 문서 구조 설계

에이전트 작업 지침(`CLAUDE.md`) 307줄은 규칙이 깨질 때마다 한 줄씩 늘었습니다.

| 규칙 | 왜 |
|---|---|
| 작업 중에 **읽지 않을** 문서를 적는다 (README·측정 기록) | 정확한 문서도 "레포에 있다"는 이유로 읽히면 컨텍스트만 차지하고 판단을 흐립니다 |
| 작업 전에 `domain.md`부터 읽는다 | 카드를 사람이 돌려 셔플·승자 판정 같은 기능은 의도적으로 없습니다. 모르면 누락으로 보고 만듭니다 |
| 코드는 줄 번호 대신 이름으로 가리킨다 | 줄 번호가 어긋나면 잡아 줄 장치가 없고, 이름은 바뀌면 `grep` 0건으로 드러납니다 |
| 문서 하나에 주제 하나 | 결함 목록 문서가 이미 고친 항목의 본문까지 품고 4,000줄을 넘겼습니다. 문서가 클수록 매 세션 드는 비용이 커집니다 |
| 문서는 메인 에이전트만, 마지막 코드 PR에 얹어 쓴다 | 문서 PR이 따로 가면 결함 목록과 코드가 어긋나는 기간이 생깁니다. 문서에 적는 현재 상태(통과한 테스트 수 등)는 머지 순서를 아는 메인 에이전트만 정할 수 있습니다 |
| 마지막 전체 리뷰는 가벼운 모델로 바꾸지 않는다 | 스킬이 작업을 지나치게 촘촘히 쪼개 조각마다 리뷰를 붙였을 때, 조각 리뷰 둘은 16분 동안 한 건도 못 찾았고 마지막 전체 리뷰 하나가 중요 결함 3건을 잡았습니다 |

## 테이블 병합 시 좌석 이동 주체를 서버에서 사람으로 전환

**문제** — 대회 막바지에는 테이블을 합칩니다. 3/3/3명을 9명 한 테이블로, 4/4/5명을 6/7명 두 테이블로 한꺼번에 옮깁니다.

**대안** — 처음에는 서버가 칩량을 보고 좌석을 재분배하려 했습니다.
- 여러 테이블을 함께 잠그는 락, 2단계 임시 좌석, 배치 계획 검증까지 설계를 마쳤습니다
- **막힌 곳**: 서버가 좌석을 옮겨도 새 자리 태블릿은 그 사람이 맞는지 모릅니다. 로그인은 원래 태블릿에 남고 사람만 걸어갑니다.

**선택** — 상점(대회를 여는 홀덤펍)은 좌석만 비우고, 사람이 칩을 들고 걸어가 폰의 참가 OTP를 새 자리 태블릿에 입력합니다.
- **8자리, 시도 제한 없음**: 대회 단위 잠금을 걸면 그 잠금이 곧 대회를 멈추는 공격 수단이 됩니다. 참가자 200명이면 6자리는 적중 확률 1/5,000, 8자리는 1/500,000입니다
- **좌석은 앉는 순간 정해집니다**: 결제할 때 정하지 않습니다

**결과** — 여러 테이블을 동시에 잠그지 않으니 교착 상태가 생길 수 없습니다.
- 좌석 예매와 Redis 좌석 락이 통째로 사라졌고, 겹치는 요청은 DB 유니크 제약이 막습니다
- 칩을 좌석 기록에서 참가 기록으로 옮겨, 좌석을 비워도 칩이 남습니다

## 서버 재시작 시 정지 시간 보정과 재개 권한 설계

**문제** — 서버가 멈췄다 돌아오면 멈춘 시간이 블라인드 시간에 그대로 들어갔습니다.

**대안** — 두 안을 거쳤습니다.
- **상점이 장애 시점을 기록하는 방식(V1 기획)**: 장애가 난 시점을 상점이 기록하고, 복구되면 그만큼 대회 시작 시각을 미뤄 기입하는 방식이었습니다. 복구는 플랫폼이 자동으로 해 주는 게 맞다고 보고 기각했습니다
- **블라인드 시간만 미루기**: 부하 테스트에서 재접속 시간을 측정하는 동안, 테스트를 지켜보던 에이전트가 코드를 따라가 남아 있던 타임아웃 잡이 재시작 직후 차례인 사람을 자동 폴드시키는 것을 찾았습니다
- 이를 계기로 복구를 다시 설계하면서 태블릿이 전부 다시 붙었는지도 알아야 했고, 상황을 가정할수록 작업이 커졌습니다

**선택** — 멈춘 시간은 서버가 계산하고, 다시 시작하는 시점은 테이블을 직접 보는 딜러가 정합니다.
- 하트비트를 DB에 5초마다 남깁니다. 주기가 곧 측정 오차라 30초에서 줄였습니다
- 시작 시각을 둘로 나눠, 실제 시작 시각은 DB에 그대로 두고 블라인드 계산용 기준 시각만 미룹니다
- **60초 유예는 없어졌습니다**: 근거 없는 임시값이었고, 다시 시작하는 시점을 딜러가 정하도록 설계가 바뀌면서 자연스럽게 빠졌습니다

**결과** — 서버가 돌아와도 그 대회의 딜러 태블릿이 모두 다시 붙기 전까지는 대회 전체를 멈춰 둡니다.
- 이 상태가 `SYNCING`입니다. 화면과 블라인드 시간이 함께 멈추고, 풀리는 순간 멈춘 시간만큼 한 번 보정합니다
- 딜러 태블릿은 좌석 태블릿보다 늦게 연결돼, 플레이어가 덜 돌아온 테이블을 먼저 시작하지 못합니다
- 상점이 콘솔에서 푸는 안(인프라 복구는 상점의 몫이 아님)과 n분 뒤 자동으로 푸는 안(그 n을 감으로 정해야 함)을 기각해, 상점이 누르는 복구용 API나 화면은 따로 만들지 않았습니다
- 딜러 복귀 수를 믿을 수 있도록, 반만 닫힌 채 살아 있는 것처럼 보이는 소켓을 10초마다 ping/pong으로 확인해 먼저 정리했습니다
- 660소켓 동시 재접속은 31.9초가 걸렸는데, 요청 상한(600)을 넘긴 소켓이 30초 동안 막혔기 때문입니다. 상한을 푼 테스트에서는 2.1초였습니다

**한계** — 복구는 핸드 단위까지입니다. 카드가 실물이라 중간에 끊긴 핸드는 딜러가 다시 딜하면 되고, 지키는 선은 "다음 핸드가 옳은 사람에게서 시작된다"까지입니다.

## 테이블 상태 쓰기 경로의 락 단일화

**문제** — 핸드 도중 늦게 온 사람을 폴드로 앉히는 설계는 있었지만, 앉는 순간 다른 사람의 액션이 같이 들어오는 레이스 컨디션이 있었습니다.
- 이 경우를 재현하는 테스트는 세 번 돌아도 실패하지 않았고, 테스트가 락을 먼저 잡게 하면 재현되지만 제품 코드는 그대로라 테스트 대신 코드를 봤습니다
- 이를 계기로 테이블 상태를 쓰는 모든 경로의 레이스 컨디션 전수조사를 시작했습니다

**원인** — 테이블 상태를 쓰는 14곳이 락을 잡고 읽고 고치고 쓰는 과정을 각자 반복했고, 락 안에서 다시 읽는 한 줄이 유일한 방어였습니다.
- 그 시점에 락 밖에서 읽은 값으로 쓰는 곳은 없어, 당장은 문제가 없었습니다
- **함정**: 그 한 줄을 지워도 실패하는 테스트가 없었습니다. 테스트가 지켜 주지 않으니, 급하게 고치다 지워도 알 수 없는 상태였습니다

**선택** — 전수조사 뒤 어디서든 안전하게 쓸 수 있는 방법을 찾아, 14곳이 각자 하던 "잠그고, 다시 읽고, 쓰기"를 함수 하나로 모았습니다.
- `mutateSnapshot`이 락·재읽기·쓰기를 맡고, 호출하는 쪽은 상태를 직접 읽지 않으니 다시 읽기를 빠뜨릴 자리가 없습니다
- 락 없이 쓰는 네 곳은 별도 함수로 이유를 남기게 하고, 이 둘 말고는 상태를 쓸 수 없게 막았습니다
- **블라인드 레벨 갱신은 락 없이**: 대회 전체가 함께 보는 값이라, 락을 걸면 한 테이블이 핸드를 시작하는 동안 다른 테이블이 시작하지 못합니다. 이유는 코드 주석에 남겼습니다
- **리바인 대기는 락 밖으로**: 최대 15초를 기다리는 동안 락을 쥐고 있어 테이블 전체가 멈췄습니다. 대상자끼리 서로 기다리면 안 된다는 조건부터 정했고, 전원에게 동시에 물어 수락한 순간에만 짧게 락을 잡습니다. 정산은 팟 분배(락 안) → 리바인 대기(락 밖) → 탈락 확정과 다음 핸드 준비(락 안)로 나뉩니다. 핸드 시작은 `WAITING`에서만 되므로 락 밖 구간에 다음 핸드가 끼어들 수 없습니다

**한계** — 핸드 전체는 다섯 구간이고 그중 둘이 락 밖인데, 그 틈을 전부 막지는 않았습니다.
- 좌석 해제나 테이블 삭제는 운영자가 쉬는 시간에 콘솔로 조작하는 일이라 핸드 도중에 들어올 일이 없습니다
- 락 대신, 전제가 깨졌을 때 조용히 틀리지 않도록 상태 검사만 남겼습니다

## 동시 접속 한계의 원인 규명과 수용 기준 재정의

**문제** — 부하 테스트로 인원을 늘려 가자 동시 착석이 11,790명에서 막혔고, 더 태우면 서버가 죽었습니다.

**원인** — 메모리가 남아 있었는데도 Node가 자기 기본 메모리 상한에 걸려 스스로 종료했습니다.
- 컨테이너 512MB 중 114MB가 남아 있었고 `OOMKilled=false`였습니다. 커널이 아니라 V8이 기본 힙 상한 259MB에서 abort한 것입니다

**대안** — 인스턴스 증설과 코드 메모리 최적화는 택하지 않았습니다.
- 인스턴스 증설: 가장 저렴한 인스턴스에서 돌린다는 기준을 벗어납니다
- 코드 메모리 최적화: 범위가 크고 효과가 불확실합니다

**선택** — 바로 할 수 있는 힙 상한 조정으로, Node의 메모리 상한을 컨테이너 여유 안쪽까지 올렸습니다.
- `--max-old-space-size=340`: 컨테이너 512MB에서 OS와 기타를 뺀 여유 안쪽입니다

**결과** — `11,790명 → 12,420명` 1,380테이블 전원 착석.
- 안정 구간: 내 조작 응답 p95 221ms, 서버 지연 중앙값 2.34ms, CPU 51.6%, 메모리 449MB
- **드러난 진짜 병목**: CPU를 12코어에서 1코어로 줄여도 서버 지연은 그대로였고, 594명이 핸드를 돌리는 동안 1코어 CPU는 6%였습니다. 테이블 하나를 세우는 비용 737ms 중 523ms(71%)가 로그인 bcrypt였습니다. 이 작업의 동시 처리 수는 CPU 코어가 아니라 Node 내부 스레드 수(기본 4)가 정해서, 로그인 요청에 상한을 뒀습니다
- **수용 기준 재정의**: 수용 인원은 동시 접속자 수가 아니라 초당 입장 수로 정해집니다. 초당 5명은 여유 있고, 초당 9~10명이면 4분 만에 응답이 느려집니다

**한계** — k6 합성 부하입니다. 실서비스 운영 기록이 아니고 장시간 소크 테스트도 하지 않았습니다.
- 22분 중 대부분이 입장 시간이라 테이블당 평균 3핸드만 돌았고 리바인은 0이었습니다. 접속과 조작의 한계를 측정한 것이지, 탈락과 리바인까지 포함한 대회 전체의 한계는 아닙니다

## 부하 측정기의 지연 오집계 결함 수정

**문제** — 턴 타임아웃을 넘기는 자리비움·장고 상황을 착석 부하 시나리오에 넣자, 부하가 거의 없는 구간에서도 응답 지연이 튀어 테스트가 중단됐습니다.
- p95 임계값 위반으로 k6가 멈췄습니다

**대안** — 일정 시간 안에 여러 번 튈 때만 멈추도록 조건을 바꿨지만 또 중단됐습니다.

**선택** — 두 번째 중단 뒤에는 조건을 더 풀지 않았습니다. 부하가 없는데 지연이 튀는 것은 서버보다 측정 쪽 문제라고 보고, 직전에 넣은 변화부터 의심했습니다.
- 생각 시간을 30.3초까지 늘려 타임아웃 뒤에 늦게 누르는 사람을 재현한 것이 원인일 수 있다고 방향을 잡고, 원인 분석을 에이전트에 맡겼습니다
- 테이블 하나짜리 유휴 서버에서 늦게 누르는 비율만 올려 재현했습니다: 기준 11.1ms, 늦은 액션 6건에서 2,585.6ms

**원인** — 서버가 아니라 측정기의 결함이었습니다.
- 타임아웃 뒤에 도착한 액션이 오지 않을 응답의 측정 창을 열고, 다음 사람의 응답이 그 창에 붙어 생각하는 시간이 서버 지연으로 기록되고 있었습니다

**결과** — 제품 코드는 그대로 두고 측정기만 고쳐, 부하 테스트를 끝까지 돌릴 수 있게 됐습니다.
- 타임아웃 뒤에 도착한 액션은 측정 창을 열지 않게 했습니다
- 고친 뒤 늦은 액션 62건이 섞인 점증 부하 테스트를 중단 없이 완주했고, 내 조작 응답 p95는 14ms였습니다

## 테스트 계층 설계와 실제 장애 검증

**문제** — 이 시스템에서 가장 위험한 결함은 목과 단위 테스트로 잡히지 않습니다.
- 목으로 테스트하면 검증 대상인 락·트랜잭션의 원자성 자체가 사라집니다
- 부품이 각각 옳아도 조립이 틀린 경우는 단위 테스트로는 잡을 수 없습니다
- 흉내 낸 장애로는 부팅 과정과 남아 있던 타이머의 실제 동작을 확인할 수 없습니다

**선택** — 각 계층이 잡을 수 있는 결함에 맞춰 테스트를 나눴습니다(통합 725 · 백엔드 단위 445 · 프론트 331 · contract 85 · e2e 13 · 부하 도구 39 · 실제 kill 26).
- **통합**: 개발용과 분리된 진짜 Redis·PostgreSQL 컨테이너로 락과 트랜잭션을 검증합니다
- **시나리오**: 사람이 읽을 수 있는 이야기라, 테스트가 맞는지를 사람이 판단할 수 있습니다
- **실제 kill**: `docker kill`로 Redis와 백엔드를 실제로 죽였다 살립니다
- **처음부터 통과하는 새 테스트는 의심**: 고친 코드를 되돌려 빨간불부터 확인합니다. 되돌려도 통과한 테스트는 다른 곳에서 이미 막고 있었거나, 막는 장치가 둘 겹쳤거나, 테스트 자체가 틀린 경우였습니다

**결과** — 프로세스를 실제로 죽이는 테스트에서, 흉내 낸 장애로는 보이지 않던 결함 세 개가 나왔습니다.
- 장애 중에도 결제는 DB에 남았지만, 전광판 참가 카운터가 에러 없이 조용히 빠지고 있었습니다
- 리바인 창이 열린 채 재시작하면, 칩을 다 잃은 사람이 등수와 상금을 받지 못한 채 좌석에서 사라졌습니다
- 마지막 탈락이 저장된 직후 연결이 끊기면 우승 상금이 나가지 않아 대회를 끝낼 수 없었습니다
